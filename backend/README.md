# Backend

FastAPI app implementing the TTS vertical slice (see the repo root [README](../README.md) and [`docs/`](../docs/README.md) for the architecture this follows — this file is just "how to run it").

## Setup

```bash
py -m venv .venv                       # or: python -m venv .venv
.venv\Scripts\activate                  # Windows; source .venv/bin/activate on macOS/Linux
pip install -e ".[dev]"

copy .env.example .env                  # then fill in the values — see .env.example's comments
```

You'll need, at minimum, to get from outside this repo:

- A **Postgres** database. Local dev, quickest path: `docker run -d --name voicica-db -e POSTGRES_USER=voicica -e POSTGRES_PASSWORD=voicica -e POSTGRES_DB=voicica -p 5432:5432 postgres:16` (matches `.env.example`'s default `DATABASE_URL`).
- A **Firebase** project's service account key ([ADR 0008](../docs/decisions/0008-auth-provider.md)) — download it from the Firebase console and save it as `../secrets/firebase-adminsdk.json` (see [`../secrets/README.md`](../secrets/README.md) — that whole folder is gitignored except its own README, on purpose, so real credentials have one findable, non-git home instead of scattering across Downloads). `.env`'s `FIREBASE_CREDENTIALS_PATH` already points there.
- A **Fish Audio** API key from <https://fish.audio/app/api-keys/>.
- A **Cloudflare R2** bucket + access key ([ADR 0004](../docs/decisions/0004-asset-mirroring-r2-retention.md)). Kie image-to-image ([ADR 0016](../docs/decisions/0016-kie-image-to-image-uploads.md)) additionally needs the bucket's **public R2.dev subdomain enabled** (bucket → Settings → Public Access — no custom domain needed) and set as `R2_PUBLIC_BASE_URL`; without it, uploading a reference image 503s rather than silently building a broken Kie request.
- An **Azure Speech** resource's key + region (Azure Portal → your Speech resource → "Keys and Endpoint" — the region matters, the API endpoint is region-specific).
- A **Google Cloud Text-to-Speech** API key (Cloud Console → APIs & Services → Credentials, with that API enabled — a plain API key is enough, no service account needed).
- A **Redis** instance ([ADR 0014](../docs/decisions/0014-background-job-execution.md)) — the arq task queue every generation job goes through now. No local Docker/WSL here, so a free-tier managed one (Upstash, Redis Cloud) is the path of least resistance, same posture as Neon for Postgres — see `.env.example`'s `REDIS_URL` comment for the exact format (note `rediss://` for TLS, which most managed providers require).
- A **Kie** API key from <https://kie.ai/api-key> ([ADR 0015](../docs/decisions/0015-kie-model-catalog.md)) — the wholesale image/video/music gateway. `PUBLIC_BASE_URL` is optional (only needed once this backend has a real public URL for Kie's webhook callback — leave it blank locally, completion still works via the poll-sweep cron, just up to ~1 minute slower).

## Run migrations

```bash
alembic upgrade head
```

This creates the schema ([`docs/data-model.md`](../docs/data-model.md)) and seeds `app_settings`' placeholder values ([ADR 0012](../docs/decisions/0012-app-settings-table.md)).

Then sync the voice catalog (Azure + Google — [ADR 0007](../docs/decisions/0007-scheduled-tasks-module.md)) before anything can use a non-default voice:

```bash
python -m app.scheduled.sync_catalog
```

Pulls each configured provider's real voice list into `voice_catalog`. Safe to re-run any time (wholesale overwrite per provider, not a diff). No scheduler runs this automatically yet — that's still ADR 0007's open item — so re-run it by hand when a provider's catalog might have changed.

## Run the app

```bash
uvicorn app.main:app --reload --port 8000
```

Or in PyCharm: the **"Backend"** run configuration (`.run/Backend.run.xml`, checked into the repo) runs the same command — pick it from the run-configuration dropdown. It uses the module's configured Python interpreter rather than a hardcoded path, so first set the project interpreter to `backend/.venv` (Settings → Project → Python Interpreter → Add → Existing → `backend/.venv/Scripts/python.exe`) if you haven't already.

Then `GET http://localhost:8000/health` should return `{"status": "ok"}`, and `http://localhost:8000/docs` has the interactive OpenAPI UI — every route needs a Firebase ID token as a bearer token except `/health`.

**The app alone won't actually generate anything now** ([ADR 0014](../docs/decisions/0014-background-job-execution.md)) — submitting a job only creates it and hands it to Redis; a separate worker process has to be running to pick it up and call the provider, and nothing about starting `uvicorn` starts one automatically. For local dev, run one combined process alongside `uvicorn`:

```bash
python -m app.worker.run_all
```

Or in PyCharm: **"Worker - All (combined)"** (`.run/Worker-All.run.xml`) — pick it from the run-configuration dropdown, same as `Backend`. This runs every provider queue (`FishAudioWorker`/`AzureWorker`/`GoogleWorker`/`KieSubmitWorker`) plus the cron sweep in one OS process (`app/worker/run_all.py`) — one thing to start instead of five, with no change to the underlying design: each queue still enforces its own concurrency cap (Fish Audio's real 5-request limit still isn't touchable by Azure/Google/Kie traffic or vice versa) exactly as if it were a separate process. The only real trade-off is that a crash takes all five down together — acceptable for local dev, not how this would actually run in production.

If you specifically want that isolation locally too (e.g. to watch one provider's worker in its own terminal, or to simulate how this deploys later — one container per queue), the five still exist as separate entrypoints and PyCharm configs: `arq app.worker.settings.FishAudioWorker` / `AzureWorker` / `GoogleWorker` / `KieSubmitWorker`, and `arq app.worker.cron.CronWorker` for the sweeps alone — **"Worker - Fish Audio"**/**"Worker - Azure"**/**"Worker - Google"**/**"Worker - Kie Submit"**/**"Worker - Cron (stuck-job + Kie poll sweep)"** in PyCharm. Don't run both the combined process and the separate ones at once — they'd double-consume the same queues.

A job just sits `pending` forever (until the stuck-job sweep eventually fails it) if the worker for its provider isn't running — if a generation seems to hang, check that the relevant `arq` process is actually up before suspecting the code.

**A real, observed characteristic worth knowing**: an `arq.Worker` does not survive a dropped Redis connection — a transient network hiccup against Upstash (`redis.exceptions.ConnectionError`/`OSError: [WinError 121] The semaphore timeout period has expired`, seen multiple separate times across long-running local dev sessions — free-tier Upstash instances close idle connections after a while) crashes the whole `run_all.py` process outright, not just that one poll iteration. Nothing currently auto-restarts it. In practice this means: if generation seems stuck and the job never resolves even after the stuck-job sweep's 15-minute window, check whether the worker process is still actually running (`tasklist`/`ps`) before assuming a code bug — a crashed worker leaves already-enqueued jobs sitting in Redis untouched until a worker restarts and picks them back up (verified: a job enqueued right before a crash ran successfully the moment `run_all.py` was started again, arq's own queue durability working as designed). A production deployment needs a real restart policy (systemd, Docker `restart: unless-stopped`, etc.) for this — not addressed here, since local dev only ever needs a manual restart.

**That crash characteristic combined with arq's own delivery guarantee to cause a second, real bug, caught live**: arq is *at-least-once*, not exactly-once — if a worker crashes after a job function's own DB commit but before arq itself acks the task in Redis, arq redelivers that already-finished task on restart. None of the three `execute_*` job functions in `services/jobs.py` guarded against this. It wasn't hypothetical: a real worker crash (the characteristic above) redelivered an already-succeeded Grok video job (`try=2, delayed=375s`), which re-ran `execute_kie_submit_job` and fired a genuine second `createTask` call at Kie — a real, wasteful duplicate video generation, confirmed by the job's `provider_job_id` being silently overwritten with a second, different real Kie taskId. The credit hold was unaffected (it was already `settled`, and `finalize_kie_job`'s own `FOR UPDATE`-guarded settlement only acts on `active` holds), but the submit-side had no equivalent guard. Fixed with two different guards, since the two failure shapes differ: `execute_tts_job`/`execute_voice_model_training_job` check `job.status in ("succeeded", "failed")` (their normal success *is* a terminal status); `execute_kie_submit_job`'s normal success leaves the job `processing` (ADR 0015 — submit and completion are deliberately separate), so its guard instead checks `job.provider_job_id is not None` — once a real `createTask` call has happened for this job, a redelivered attempt has nothing safe left to do. The one job corrupted by this before the fix landed was on the dedicated test account and has been manually restored (its status field was wrong; its actual R2 asset was never touched).

## Deploy

Render ([ADR 0023](../docs/decisions/0023-backend-deploy-render-singapore.md)) — two services from this same repo (`Root Directory: backend`), both on the free plan for now, both in the **Singapore** region (matching Neon and Upstash — see the ADR for why same-region matters here):

- **Web Service** `voicica-api` — Build: `pip install -e . && alembic upgrade head`. Start: `uvicorn app.main:app --host 0.0.0.0 --port $PORT`.
- **Background Worker** `voicica-worker` — Build: `pip install -e .` (no migration — the web service's build already ran it). Start: `python -m app.worker.run_all`.

**Don't just copy `.env` wholesale into Render's environment variables** — a few keys need a genuinely different value in production, not the local-dev one:

| Key | Local value | Production value |
|---|---|---|
| `CORS_ALLOW_ORIGINS` | `["http://localhost:3000"]` | `["https://voicica.ai","https://www.voicica.ai"]` — copying the local value here silently blocks every request from the real frontend (`Disallowed CORS origin`, caught live on the first real deploy) |
| `PUBLIC_BASE_URL` | blank | the service's own real URL (e.g. `https://voicica-api.onrender.com`) — lets Kie's webhook callback reach this backend directly instead of falling back to the ~1-minute poll-sweep every time |

Everything else (`DATABASE_URL`, `REDIS_URL`, `FIREBASE_CREDENTIALS_JSON`, every provider API key, R2 credentials) is the same real value in both places — those aren't secrets that differ by environment, just secrets, so the local `.env` value is the production value too.

## What's implemented (this slice)

- `POST /generate/tts` → `GET /jobs/{id}` / `GET /jobs` — submit and read back a TTS job, credits held/settled/released around it ([ADR 0002](../docs/decisions/0002-unified-async-job-model.md), [ADR 0003](../docs/decisions/0003-credit-ledger-hold-then-settle.md)). **Exactly one of `voice_id`/`voice_model_id` is required** — which provider gets called is decided entirely by whichever voice was resolved (a `voice_catalog` row, or a user's own `voice_models` row, ADR 0009), not a separate provider field (architecture.md §3c, `services/jobs.py submit_tts`). Fish Audio isn't a general fallback, it's reserved for a user's own cloned voices — an earlier version of this defaulted to Fish Audio's own generic voice when no `voice_id` was given, which had nothing to do with what the picker actually offers; corrected once that was pointed out. Optional `speed`/`volume`/`pitch` (0.5-2.0x / 1-100 / 1-100, one scale for every provider) get converted to each adapter's own units — exact formulas ported from the prior project's verified-in-production conversions, not re-derived; Fish Audio has no pitch control and ignores that one; some Google voices (Chirp3 HD) reject `pitch` outright, so `providers/google.py` retries once without it on that specific error rather than failing the whole request. Fish Audio's TTS model (`s2.1-pro`, their current recommended model — the prior project's `speech-1.5`/`speech-1.6` were deprecated by Fish Audio on 2026-02-28, so weren't carried forward) is an `app_settings` value (`fish_tts_model`, [ADR 0012](../docs/decisions/0012-app-settings-table.md)), not a hardcoded constant — read fresh per-request in `services/jobs.py submit_tts`, same as `tts_credits_per_10_chars`, so bumping it to whatever Fish recommends next is `PATCH /admin/settings/fish_tts_model`, no deploy. Verified: reading the default, writing a different value and seeing a fresh read reflect it immediately (no restart, no caching), and a real Fish Audio call succeeding with that value in the header — then restored to `s2.1-pro`.
- `GET /catalog/voices?provider=&locale=&language=` / `GET /catalog/languages?provider=` — the synced voice picker data. Azure + Google's real catalogs (`app/scheduled/sync_catalog.py`), every language either supports (82 distinct base languages, 158 locale variants) — no target-market restriction; the picker keeps its payload small by always fetching one *language*'s voices at a time (`language=es` matches every `es-*` locale across every provider), not by narrowing which languages exist or by picking one exact locale (`services/voice_catalog.py`'s module docstring explains all three corrections here — availability, exact-locale-vs-base-language, and Google's `cmn`/Azure's `zh` both meaning Mandarin Chinese, aliased at the query layer only since the *stored* `locale` on a voice is also what gets sent back to that provider at generation time and must stay exact). Fish Audio's isn't synced yet (see ADR 0007's open items).
- `POST /voice-models` → `GET /voice-models` / `DELETE /voice-models/{id}` — voice cloning (ADR 0009, Fish Audio only). Training is multipart (a sample audio file + a name + an optional transcript), and turned out synchronous — `train_mode="fast"` (the only mode used; `"full"` mode's timing isn't verified, so isn't exposed) already returns `state: "trained"` in the create response, no polling needed, same shape as a TTS job. Free (`estimated_cost=0`, still through the ordinary hold->settle lifecycle for audit-trail parity) — ports the prior project's own real pricing (it never charged for cloning, only for *using* a clone). A trained voice's id then goes into `POST /generate/tts`'s `voice_model_id`, priced and routed exactly like a catalog voice.
- `GET /me` — current user + wallet balance; first call for a new Firebase identity bootstraps a local `users` row, a wallet, and the signup bonus.
- `PATCH /jobs/{id}` — mark a job public after the fact; `POST /generate/tts`'s `visibility` also does this at creation time, both set the same field ([ADR 0010](../docs/decisions/0010-public-gallery-visibility-flag.md)).
- `GET /gallery` — the public gallery: cursor-paginated `visibility: public` jobs with a ready asset, no auth dependency (`app/services/gallery.py`). `GET /jobs/{id}/asset` now lets any logged-in user through for a public job's asset, not just the owner.
- `/admin/*` — manual credit grants, job listing, settings read/write, capability-menu CRUD ([ADR 0012](../docs/decisions/0012-app-settings-table.md)), Kie catalog CRUD. Has a real UI now — `frontend/web`'s `(admin)` route group ([ADR 0020](../docs/decisions/0020-admin-folded-into-web.md)) — but every route here is still directly callable (`/docs`, curl, Postman) for anything the UI doesn't cover yet.
- **Background job execution** ([ADR 0014](../docs/decisions/0014-background-job-execution.md)) — every `POST /generate/tts`/`POST /voice-models`/`POST /generate/kie` now only creates the job and hands it to a Redis queue (`app/core/queue.py`); the actual provider call happens in an `arq` worker task (`app/worker/tasks.py`, `services/jobs.py`'s `execute_*` functions), never inline in the request. Queues are split per provider (`app/worker/settings.py`) so Fish Audio's real, observed 5-concurrent-request limit can't delay Azure/Google/Kie jobs or vice versa. The stuck-job sweep ([ADR 0007](../docs/decisions/0007-scheduled-tasks-module.md)'s other half) and the Kie poll-sweep (below) both run as arq cron jobs (`app/worker/cron.py`), every 5 and 1 minutes respectively. `app/worker/run_all.py` runs everything above in one process for local dev — same underlying design, still independent `arq.Worker` instances each with their own concurrency cap, just sharing one OS process.
- **Kie image generation** ([ADR 0015](../docs/decisions/0015-kie-model-catalog.md)) — `POST /generate/kie` (`{model_id, inputs, visibility}`) + `GET /kie/categories`/`GET /kie/models?category_id=`/`GET /kie/models/{model_id}` (the schema-driven catalog a generic frontend form reads) + `POST/PATCH/DELETE /admin/kie-*` (add/edit/remove a model or category — no deploy). `providers/kie.py` has zero per-model code: `model` and `input` are opaque values from the catalog, sent to Kie's one real `createTask` endpoint verbatim. Unlike every other provider here, Kie is genuinely async — `submit()` always returns `processing`, and completion arrives later via `POST /webhooks/kie` (primary) or the 1-minute poll-sweep cron (fallback), both funneling into the same `services/jobs.py finalize_kie_job()`. Three real categories now: `text-to-image` (4 models — Flux-2 Pro/Flex, GPT Image 2.5 Flare/Sunburst), `image-to-image` ([ADR 0016](../docs/decisions/0016-kie-image-to-image-uploads.md), same 4 model families' image-to-image sibling `model_id`s — `POST /kie/uploads` gives a reference image a short-lived public R2 URL Kie's own servers can fetch, Kie takes URLs, never a file upload or base64, deleted the moment its job reaches any terminal state via `services/jobs.py cleanup_kie_uploads`), and `image-to-video` ([ADR 0017](../docs/decisions/0017-kie-video-and-catalog-splitting.md), the first `output_type: "video"` category — Grok Imagine Video 1.5 and Veo 3.1 Lite both live). ADR 0017 also added `kie_models.provider_model_id`/`fixed_inputs`, so a catalog row's own id no longer has to equal the literal string sent to Kie — needed once Veo 3.1's Lite/Fast/Quality tiers turned out to all be `provider_model_id="veo-3-1"` under the hood — and a third pricing shape (`rate_param`/`tier_param`/`rates`) for genuine per-second billing, real-verified to match Kie's own `creditsConsumed` exactly.

Not implemented yet, by design (see [`docs/flows.md`](../docs/flows.md) for the full list): Kie music categories (not catalogued yet), Veo 3.1's Fast/Quality tiers (staged deliberately — Lite first, now live and verified), whether Azure/Google support an equivalent to voice cloning (ADR 0009's own open item — Fish Audio is the only provider this covers), real payment top-up, an actual scheduling mechanism for `sync_catalog.py` (manual for now, even though arq's cron — now proven working for two different sweeps — could run it too; nothing forces that move yet).

Verified end-to-end against real infrastructure — Neon, Firebase, Fish Audio, R2, **and now real Azure Speech + Google Cloud TTS accounts**: sign in → submit a TTS job (all three providers, including Thai and Spanish voices for the target market) → real synthesis → real R2 upload → read the job back → mark it public → credits debited correctly. Catalog sync pulled 779 real Azure voices and 2066 real Google voices (82 distinct base languages after the cmn/zh merge below) on the last run. The frontend's "Select a voice" picker (`frontend/web/components/VoiceSheet.tsx`) is built and verified too — language dropdown (popular languages first, all 82 selectable, grouped by base language so e.g. "Spanish" pulls in both Azure's ~22 country locales and Google's 2, and "Chinese" pulls in both Azure's `zh-*` and Google's `cmn-*`), gender/provider filters, search, all against real synced data; picked voices actually route to the right provider end-to-end (confirmed with a Thai Google voice, a Mexican-Spanish Azure voice, and a Mandarin Google voice through real requests). Also caught and fixed: Azure locale codes with a third segment (`zh-CN-guangxi`, `sr-Latn-RS`, `iu-Cans-CA`) were all displaying as their base "{Language} ({Region})" name with the distinguishing part silently dropped — `frontend/web/lib/locale-names.ts` now parses script subtags and Azure's own dialect labels properly.

Audio Settings (speed/volume/pitch) verified end-to-end too, across real, non-default values in several requests: Azure (speed 0.7x/volume 30/pitch 20, and separately volume 75% via the actual browser UI), a Google Chirp3 HD voice (confirms the pitch-unsupported retry actually fires and still succeeds — both via a direct request and, separately, the real browser UI with pitch 30), and a Google Standard voice (pitch supported directly, no retry needed). The Fish Audio default path was verified too, before `voice_id` became required (speed 1.5x/pitch 85 via the actual browser UI) — the conversion logic itself hasn't changed since, only that this path is no longer reachable without an explicit voice.

The public gallery is verified end-to-end too: `GET /gallery` returns real public jobs with real pagination (`limit`/`next_cursor` tested against 8+ real rows); a non-owner logged-in user can fetch a public job's asset (200, real audio bytes) but still gets 404 on a private one; setting `visibility: "public"` at creation time (`POST /generate/tts`) makes a job appear in the gallery immediately, confirmed through the real browser (generate with "Share to Explore" on → the same job shows up on the Explore/Home page). The frontend also caught and fixed a real race condition here: switching between two gallery items' playback quickly could silently stop both, because the *previous* item's now-superseded `play()` promise rejects (`AbortError`, browser-standard behavior when `.src` changes mid-request) *after* the newly-clicked item's state was already set, and the original error handler blindly cleared `playingId` regardless of whose rejection it was — fixed by only clearing it if `playingId` still points at the item that failed.

Voice cloning (ADR 0009) is verified end-to-end against the real Fish Audio API and a real browser round trip (`/app/create/clone`): recorded/uploaded a sample → `POST /voice-models` (multipart) trained a real model → confirmed synchronous (`state: "trained"` in the create response itself, no polling — corrected an earlier assumption in architecture.md §3e that this needed Kie-style polling) → the new voice appeared in `GET /voice-models` immediately → generated real speech with it via `POST /generate/tts`'s `voice_model_id` (routed to Fish Audio, 7 credits charged at the ordinary per-character rate, real audio played back) → deleted it (`DELETE /voice-models/{id}`, 204). Training itself cost 0 credits, confirming the free-training decision works through the real hold→settle path. Caught and fixed a real bug along the way: deleting a voice model 503'd with a `ForeignKeyViolationError` — `jobs.voice_model_id`'s FK defaulted to Postgres's `RESTRICT`, which blocks the delete whenever any job (its own training job, or a TTS job that used it — always true) still references it; fixed with `ON DELETE SET NULL` (migration `0007`). Also observed: Fish Audio's own `DELETE /model/{id}` 404'd even though the model had been used successfully seconds earlier (an external quirk, not caught as a bug in this integration) — the best-effort design (log it, remove the local row regardless) meant this didn't block the user-facing delete, which is exactly what it's for.

Background job execution (ADR 0014) is verified end-to-end against a real Upstash Redis instance, not a local/fake one: a real `POST /generate/tts` (Azure) and a real train-then-speak round trip through Fish Audio (`POST /voice-models` then `POST /generate/tts` with the resulting `voice_model_id`) both returned `202`/`status: "pending"` immediately and were picked up and completed seconds later by separately-running `AzureWorker`/`FishAudioWorker` processes — confirmed both from the API response (polled `GET /jobs/{id}` to `succeeded`) and from each worker's own log line showing it picked up that exact job id. `app/worker/run_all.py` (all four in one process) was verified the same way afterward, including that arq's own per-job log lines actually show up (they don't by default outside the `arq` CLI — `run_all.py` replicates the CLI's own `logging.config.dictConfig(default_log_config(...))` call, or every "picked up"/"finished" line silently disappears). The full real-browser UI flow (type text → pick a voice → Generate → the page's own poll loop → result) was verified too, not just direct API calls. `sweep_stuck_jobs` was dry-run against the real database (0 stuck jobs at the time, as expected — everything else in this pass completed normally). One real, unrelated latency finding along the way: the first few requests each session pay a multi-second penalty inside `credits.estimate_tts_cost()`'s first DB query — a Neon free-tier compute cold-start, not anything introduced by the queue (`enqueue()` itself measured ~110ms warm, ~220ms cold, in isolation) — noted here rather than glossed over since it's a real, observable characteristic of local dev against this database.

**Kie image generation (ADR 0015) is verified end-to-end against real infrastructure**, including a real failure along the way, not just the happy path: a real `flux-2/pro-text-to-image` job (submitted directly through `services/jobs.py submit_kie_job`, since no frontend page exists yet) went `pending` → real `202`-equivalent in milliseconds → the `queue:kie-submit` worker called Kie's actual `createTask` and got back a real `taskId` → polling Kie's real `recordInfo` showed `success` within seconds → the real image was downloaded and mirrored to R2 (`GET /jobs/{id}/asset` served a genuine 1.45MB PNG matching the prompt) → the wallet was debited exactly 5 credits, matching Kie's own reported `creditsConsumed` exactly (settlement is 1:1 from that number, not a separate formula). Along the way, a first attempt failed for real and surfaced two genuine findings, not injected on purpose: (1) `flux-2/pro-text-to-image` actually requires a `resolution` field Kie's own simplified playground Form view doesn't show — found only by making the real call, then fixed live via `PATCH /admin/kie-models/flux-2%2Fpro-text-to-image` with zero downtime, exactly the workflow ADR 0015 exists to enable; (2) Kie returns **HTTP 500**, not 400, for that kind of input-validation rejection, which this codebase's shared `_is_transient_error()` heuristic (5xx = transient, worth retrying) treats as retryable — so a genuinely broken `input_schema` costs ~15s of wasted retries before failing for real, rather than failing immediately. No charge either way (the failed job's hold was fully released, confirmed against the test account's real balance), so this is a latency cost, not a correctness bug — noted in `architecture.md §3d` rather than special-cased in code, since the actual fix is keeping the catalog's `input_schema` accurate, not teaching the shared retry heuristic about one vendor's quirky status codes.

**Kie image-to-image (ADR 0016) is verified end-to-end against real infrastructure**, including the one leg that couldn't be checked until `R2_PUBLIC_BASE_URL` was actually set up (a real Cloudflare R2 bucket's public `pub-<hash>.r2.dev` dev URL, no custom domain): uploaded a real photo (a previously-generated robot-in-a-window image) to R2's public prefix -> submitted a real `flux-2/pro-image-to-image` job with that URL in `input_urls` and the prompt "add a small chef's hat and a name tag that says 'PIXEL'" -> Kie's real `createTask` succeeded -> polling showed `success` -> the result (downloaded and inspected) genuinely applied the edit — the same robot, same scene, now wearing a chef's hat with a "PIXEL" name tag, confirming Kie actually fetched and used the uploaded reference rather than ignoring it -> `actual_cost` settled at exactly 5 credits -> **and the uploaded reference image was confirmed gone from R2 immediately after** (`assets_service.download_bytes` on its own key raised `NoSuchKey`), proving `cleanup_kie_uploads` actually runs and actually works, not just that the code exists. Separately, the "Image to Image" category page and `flux-2/pro-image-to-image`'s full 5-field generation form (including the brand-new `image`-type field) were verified rendering correctly through the real browser with zero page-specific code.

**Kie video generation (ADR 0017) is verified end-to-end against real infrastructure**, including the new per-unit pricing shape actually matching Kie's own billing: submitted a real `grok-imagine-video-1-5-preview` job (a real uploaded reference photo, `duration: 5` at `480p`) → `estimated_cost` computed as `ceil(2.4 * 5) = 12` credits from the new `rate_param`/`tier_param`/`rates` pricing shape → Kie's real `createTask` succeeded → polling reached `success` in under a minute → a genuine 1.3MB MP4 (`video/mp4`, correctly mapped to a `.mp4` R2 key) was mirrored → **`actual_cost` settled at exactly 12 credits — Kie's own `creditsConsumed` matched this catalog's estimate exactly**, real confirmation the per-second rate (2.4 credits/sec at 480p, copied from Kie's own pricing text) is accurate, not just plausible → the uploaded reference was confirmed gone from R2 immediately after, same as image-to-image. The generic generation form rendered all 6 of this model's real fields (prompt, reference image, aspect ratio, resolution, duration, NSFW filter) correctly with zero page-specific code, and the result page's new `<video>` branch (the first non-image `output_type`) was exercised for real. **Verified at the service layer, not by clicking the real upload button in a browser** — this environment's browser-automation tooling can only upload files the user explicitly shared with the session, not arbitrary local files, so the literal "click Add images, pick a file" interaction remains the one unexercised leg (ordinary React file-input code, already proven correct for image-to-image's identical `ImageField` component).

**Veo 3.1 Lite is now also live, after a real schema correction caught mid-verification.** Its `fixed_inputs` value (`"veo3_lite"`) was confirmed for real — Kie's own account dashboard (`kie.ai/logs`) showed the exact request body for a successful, 30-credit 720p job with `"model":"veo3_lite"` in it. But that same dashboard log revealed the *rest* of the first schema attempt was wrong: it had been built from the Playground's UI shape (separate Start Frame / End Frame image inputs, a guessed `aspect_ratio` casing, no `duration` field at all) rather than Kie's actual published `createTask` body-params reference for `veo-3-1`. Checking that reference directly turned up several real mismatches at once — worth internalizing as a pattern, not just fixing once: **Kie's dashboard Logs page renders request bodies in an internal camelCase shape** (`imageUrls`, `aspectRatio`, `generationType`, `waterMark`) that is *not* what `POST /api/v1/jobs/createTask` actually accepts on the wire (that's `image_urls`, `aspect_ratio`, `generation_type`, `watermark`, snake_case, per the docs) — trust the published param reference over the dashboard's own display format. The real shape: a single `image_urls` array (1 image = single reference frame, 2 = first+last frame — not two separate fields), `generation_type` left **unset** entirely (Kie auto-derives it from whether `image_urls` is present, conveniently sidestepping a real gap in `fixed_inputs` — it only holds static values, not ones that depend on another input field being filled in), `enable_fallback` dropped (documented deprecated), and `duration` turned out to be a real, fully-documented field after all (enum `4`/`6`/`8`, default `8` — doesn't affect Veo's flat per-video price). Corrected schema re-verified end-to-end through our own `submit_kie_job` (not Kie's website): real 30-credit Lite/720p job, `estimated_cost` matched Kie's own `creditsConsumed` exactly, a real ~2.2MB MP4 mirrored to R2, reference upload cleaned up after. Fast/Quality tiers stay deferred — same mechanism, `fixed_inputs={"model": "veo3_quality"}` is an inference from the now twice-confirmed naming pattern, not independently checked yet.

**Two more real UX gaps, both caught by inspection right after this shipped, both about the same underlying mistake** — describing a numeric range in `note` text isn't the same as actually enforcing it:
- Veo's `duration` had gone in as a `type: "number"` free-text field, but Kie's own enum only allows `4`/`6`/`8` — nothing stopped a user typing `5` or `100`, which Kie would only reject at submission. Fixed by adding a `numeric: true` flag `KieInputField` now supports (`lib/api.ts`) — a `select` field that sends the option as a real JS number instead of its string, so Veo's duration renders as three quick-pick pills (`4`/`6`/`8`) like `aspect_ratio`/`resolution` already do, with no way to type an invalid value at all.
- Grok's `duration` is a genuine continuous range (`[1, 15]`), so a `select` doesn't fit it — but its own `number` field had the identical problem one level up: nothing stopped `999`. Rather than just clamping a free-text field (a `min`/`max`-bounded onBlur clamp was tried first, but a user could still type garbage before blurring, or submit via Enter before the blur fires), added a new `slider` field type (`KieInputField`) matching Kie's own dashboard UI for this exact field — a range input whose displayed value is read-only, not editable text, so it's physically impossible to produce a value outside `[min, max]` rather than merely inconvenient to. Verified live: dragging/keyboard-stepping to either end clamps at 1 and 15 exactly, and the live cost estimate (`ceil(2.4 × duration)`) recalculates correctly at both ends (3 credits at 1s, 36 at 15s).

**A second real incident, right after that first round of testing**: `voice_models` originally had no `title` column at all — `GET /voice-models` returned only `{id, provider, state, created_at}`, so every voice rendered as an identical, indistinguishable placeholder in the picker. That's exactly how a real user's just-trained voice got mistaken for leftover test data and deleted during a cleanup pass. Fixed by adding `title` (migration `0008`, backfilled from the name already typed into `POST /voice-models`' `title` form field, which was being sent to Fish Audio but never persisted on our own row) and making sure it's always rendered wherever a cloned voice is listed. The lesson generalizes past this one table: **a resource a person creates through the UI needs a stored, displayed name before anything (a person, or an agent) can safely tell instances of it apart** — a generic list of otherwise-identical rows is an invitation to delete the wrong one.

**Real-time job completion (ADR 0018) is built and verified end-to-end against real infrastructure**, resolving a real, user-caught UX problem: every create page used to block on `pollJob()` right there on the same screen, fine for TTS (a few seconds) but genuinely bad for Kie image/video (routinely 30s-several minutes) — a real screenshot of a Kie form sitting on "Generating…" is what prompted this. `services/jobs.py publish_job_event()` (called at every terminal-state write — `_complete_success`, `_complete_kie_success`, `_complete_failure`, `execute_voice_model_training_job`'s own success branch, and `worker/cron.py sweep_stuck_jobs`'s timeout path) publishes to the job's owner's own Redis channel (`job-events:{user_id}`, reusing the pool ADR 0014 already opened for arq — no new external dependency); `GET /events` (`api/routes_events.py`) subscribes per connected user and forwards each message as Server-Sent Events. Every create page now submits and returns immediately; `/app/me` is where a result is actually viewed, live-patching the one row an event names via a fresh `GET /jobs/{id}` rather than trusting the event payload to carry a full job body.

Verified for real, not just wired up: submitted a real Azure TTS job through the actual browser, watched `BottomNav`'s pending-count badge go `1 → 2` on submit (the toast fired too, confirmed via a decrementing badge even on a run where the toast itself was missed mid-screenshot), the real worker process pick it up and finish it, the badge drop back `2 → 1` the instant the SSE event arrived — no reload, no poll — and `/app/me`'s own card for that job live-patch from a spinner to a real, working `<audio controls>` element. Caught one real testing mistake along the way worth recording as a pattern, not a bug: a voice-selection sheet that visually looked selected but whose click hadn't actually registered made the very first two "submit" attempts silently no-op (`Generate` stayed enabled but nothing hit `POST /generate/tts` — confirmed via `read_network_requests`, not assumed) — a reminder that a UI that *looks* interacted-with isn't proof a click landed; check the actual network request, not the screenshot, when a test's result looks surprising.

Two real, independent instances of the already-documented "arq doesn't survive a dropped Redis connection" crash happened again while building and verifying this feature (the worker died mid-test both times, restarted clean both times, already-queued jobs picked back up exactly as documented above) — not a new finding, just further confirmation it's a real, recurring characteristic of this environment's Upstash connection, not a one-off.

**Auth for this one endpoint is deliberately different from every other route**: the token travels as `?token=` because the browser's native `EventSource` can't set custom headers, so it can't send the usual `Authorization: Bearer`. The dependency that resolves it opens its own short-lived DB session (committed and closed before the route's actual SSE generator starts) rather than `Depends(get_db)`, whose session would otherwise sit open — holding a pooled connection — for as long as the SSE connection itself does, which can be a long time.

## Conventions (found the hard way — keep following them)

- **Every timestamp column is `DateTime(timezone=True)`** in `models/models.py`, matching `timestamptz` in the migrations. Omitting it compiles fine but fails at runtime the first time a tz-aware Python `datetime` (i.e. anything from `datetime.now(UTC)`, which is the only correct way to build one here) gets bound to that column.
- **Any route that writes data must `await db.commit()` explicitly before returning**, not rely on `get_db()`'s post-`yield` commit alone. In this FastAPI/Starlette combination, that generator-dependency cleanup can run *after* the response has already been sent — so a client that immediately re-reads what it just wrote (the normal "submit, then poll" pattern) can race the commit and see stale/missing data. Every existing write endpoint (`jobs.submit_tts`, `PATCH /jobs/{id}`, the `/admin/*` writes) already does this; keep the pattern for any new one.
- **A long-running `uvicorn --reload` process can silently stop picking up new files** — new routers/modules specifically, not just edits to existing ones. Caught this the hard way: a whole new router (`routes_catalog.py`) plus a changed request field (`reference_id` → `voice_id`) were added, `/health` kept responding fine, and a browser test even "passed" — because Pydantic silently ignores an unknown extra field, so the frontend's new `voice_id` was dropped and the request fell through to the *old* code's default behavior. **If a route added or changed this session 404s, or a change doesn't seem to take effect, don't trust the dev server — check `curl localhost:8000/openapi.json` for the route, and if it's missing, kill the process and restart it** rather than assuming the code is wrong.
- **A nullable FK needs its `ondelete` behavior stated explicitly, not left at Postgres's default `RESTRICT`** — `jobs.voice_model_id` was written as `ForeignKey("voice_models.id")` with no `ondelete`, which compiles and migrates fine and only breaks the first time someone actually deletes a referenced row (`DELETE /voice-models/{id}` 503'd, real bug caught via a real browser test — see ADR 0009). If a nullable reference is meant to survive the thing it points to being deleted (a job's history outliving a voice the user later removes), say `ondelete="SET NULL"` on the column *and* match it in the migration's `op.create_foreign_key(..., ondelete=...)` — SQLAlchemy's own default is `NO ACTION`/`RESTRICT`, not "leave the reference dangling."
- **A migration that seeds data by importing a live constant from application code (not a static snapshot) only stays correct as long as migrations keep running one at a time, as each is written** — `0009_kie_catalog.py` imported `app/services/kie_catalog.py`'s `_SEED_CATEGORIES`/`_SEED_MODELS` unfiltered, which was fine when it first ran (the constant only had `text-to-image` in it yet) but broke the first time the *entire* chain ran fresh against an empty database (standing up the Singapore Neon project) — by then the constant had grown to include `0010`/`0011`'s categories too, so `0009` bulk-inserted everything, and `0010` then hit a duplicate-primary-key error re-inserting `image-to-image`. `0010`/`0011` already filter the shared constant down to just the category ID(s) they're each responsible for (`_NEW_CATEGORY_IDS = {...}`) — `0009` predates that pattern and needed the same fix. **Every migration that seeds from a shared, still-growing constant must filter to exactly what it introduced, not trust the constant's current shape** — the bug is invisible until someone actually runs the full chain against a genuinely empty database, which local dev never does (Postgres wraps a whole `upgrade head` invocation in one transaction, so the failure rolled `0001`-`0009` back too — cleanly, nothing to hand-clean up).
