# frontend/web

Next.js app (ADR 0011) with two route groups: `(app)` (everything behind login) and `(marketing)` (public, no login — ADR 0019) — see the repo root [README](../../README.md) and [`docs/`](../../docs/README.md) for the architecture. `/` is now `(marketing)`'s real homepage, not a placeholder redirect — the authenticated app lives under a literal `/app` URL prefix, not the root (a route group alone doesn't affect the URL; the `app/(app)/app/` folder nesting is what actually puts `/app` in the path — caught and fixed once already, don't regress it).

## Setup

```bash
npm install
cp .env.local.example .env.local   # fill in NEXT_PUBLIC_FIREBASE_* (already has real values — see below) and NEXT_PUBLIC_API_BASE_URL
npm run dev
```

Or in PyCharm/WebStorm: the **"Web"** run configuration (`.run/Web.run.xml`, checked into the repo) runs `npm run dev` against this project — pick it from the run-configuration dropdown. It uses the project's configured Node interpreter, not a hardcoded path.

The Firebase web config in `.env.local.example` is already filled in — it's meant to be public (see the file's own comment) — project `ai-voice-labs-473713`, reused from the prior project on purpose (`CLAUDE.md`). `NEXT_PUBLIC_API_BASE_URL` should point at the backend (`http://localhost:8000` for local dev, per `backend/README.md`).

## What's here

- `lib/firebase.ts` / `lib/auth-context.tsx` — Firebase Auth (email/password + Google, both enabled on the shared Firebase project), exposed via `useAuth()`.
- `lib/api.ts` — the one place that calls the backend: attaches the Firebase ID token, unwraps `docs/api-contract.md`'s `{"error": {code, message}}` envelope into a typed `ApiError`. `pollJob()` repeatedly calls `GET /jobs/{id}` until a terminal status — genuinely required since [ADR 0014](../../docs/decisions/0014-background-job-execution.md): a submit call's own response is always `pending` now, the provider call happens in a backend worker.
- `lib/locale.ts` — `(app)`'s locale preference, a cookie not a URL segment ([ADR 0013](../../docs/decisions/0013-i18n-routing-strategy.md)).
- `lib/locale-names.ts` — presentational-only helpers: `localeDisplayName()` (locale code → human name, via `Intl.DisplayNames`) and `friendlyVoiceName()` (cleans up Google's raw voice-id display names). Used by `components/VoiceSheet.tsx` and the TTS create page.
- `lib/audio-settings.ts` — speed/volume/pitch types, ranges, defaults, and the `useAudioSettings()` localStorage-backed hook. Used by `components/AudioSettingsSheet.tsx` and the TTS/clone create pages.
- `components/AudioRecorder.tsx` — records (MediaRecorder, webm/opus, 30s cap — ported from the prior project's own `AudioUploader.tsx`) or accepts an uploaded file for a voice-cloning sample. Used by `create/clone/`'s Clone tab.
- `app/login/` — sign in / sign up.
- `app/(marketing)/` — the public site (ADR 0019): `/` (home), `/voice`, `/image`, `/video`, `/privacy`, `/terms`, `/contact`. `layout.tsx` is a client component (reads `useAuth()` to show "Sign in"/"Get started" vs. "Go to app") wrapping server-rendered pages, so page content still SSRs for SEO. Content lives in `content/marketing/en.ts` (typed against `content/marketing/types.ts`) rather than inline JSX strings — English only for now; `/th`, `/id`, `/es` are not built and genuinely 404 (not empty placeholders, not machine-translated stand-ins — see the ADR for why). `lib/marketing-seo.ts` builds canonical/`hreflang` URLs off a `MARKETING_LOCALES` registry (currently just `en`) so registering a real new language later is additive there too. The homepage's "Made with Voicica" strip pulls real, unauthenticated `GET /gallery` data (captions/provider/date) — text-only, since the asset-bytes endpoint still requires a logged-in viewer (see ADR 0019 on why that wasn't widened as a side effect here). `/contact` shows a real name/email/address specifically because a Payoneer payout-account application requires a live site showing at least two of those; the address is intentionally public for now, meant to come down once verification clears.
- `app/sitemap.ts` / `app/robots.ts` — Next's file-convention routes, served at `/sitemap.xml`/`/robots.txt`. The sitemap lists exactly `(marketing)`'s 7 pages (a fixed list, mirroring ADR 0019's page scope — add a row when a page is added) with a real static `lastModified` (bumped by hand when a page's content actually changes, not `new Date()` recomputed every build) and per-page `hreflang` alternates via the same `MARKETING_LOCALES` registry as everything else. `robots.txt` disallows `/app` (never crawled, ADR 0013) and points at the sitemap.
- `app/(app)/app/` — everything behind login (ADR 0005), served at `/app`: `layout.tsx` (one level up, `app/(app)/layout.tsx`) gates on Firebase auth state and renders the bottom nav; `page.tsx` is Home = "Explore" (the bottom nav's label) — the **public gallery** (ADR 0010, `GET /gallery`), not the signed-in user's own history; that mix-up existed for a while and was caught in review, see "Verified" below. `create/tts/` is the TTS flow (submit → inline result with playback + the public/private toggle, now settable before generating too — see below); `create/clone/` is voice cloning (ADR 0009 — see below); `me/` is the profile + the signed-in user's own full history (`GET /jobs`, unchanged).
- `app/(app)/app/create/kie/[categoryId]/` (model list) + `.../[modelId]/` (generation form + result) — the Kie generation surface (ADR 0015/0016/0017), both pages generic over which category/model they're given, not written for "images" or "videos" specifically. `[categoryId]` fetches `GET /kie/categories`/`GET /kie/models?category_id=` and lists cards (reusing `CreateSheet`'s row style); `[modelId]` fetches `GET /kie/models/{id}` and renders a form purely from `input_schema` — all five real field types now (`text`/`select`/`number`/`boolean`/`image`), with a live cost estimate (`estimateKieCost()` in `lib/api.ts`, mirroring the backend's own three pricing-rule shapes, including ADR 0017's per-unit rate) next to the Generate button. An `image` field (`ImageField`, ADR 0016) uploads each file via `api.uploadKieReference()` the moment it's picked — not deferred to submission — collecting the resulting public URLs into that field's value; only when Generate is pressed does `api.submitKie()` also send along every upload's `r2_key` so the backend can delete them once the job finishes. `KieResultView` renders `<img>` or `<video controls>` based on the model's `output_type` (denormalized onto `KieModel`, ADR 0017) — a future audio category needs its own branch added there. A real `model_id` can contain a literal `/` (e.g. `flux-2/pro-text-to-image`) — always percent-encoded, both in the link `href` and the API call.
- `components/BottomNav.tsx` + `components/CreateSheet.tsx` — the "+" button opens a bottom sheet, not a direct link. **The sheet's contents are entirely server-driven** (`GET /config/menu`, `docs/api-contract.md`'s "Capability menu" section / `backend/app/services/menu.py`) — labels, routes, enabled/disabled, order, badges, all come from the backend, already resolved to one locale. The frontend's only local config is `components/icons.tsx`, a small icon-key → SVG lookup (the one deliberate exception — "前端基本上没有任何配置" doesn't cover presentational icon markup). TTS and voice cloning are enabled; the other three (dialogue/image/bg-remove, plus video-download) exist in the seed data disabled, waiting on their own backend slices.
- `public/brand/` — the prior project's logo assets, reused as-is (`mark.webp`/`mark-512.webp` for the toucan mark, `credits-token.png` for the credits pill icon) — see `CLAUDE.md` on why: the old logo was good, no reason to redo it.

Visual language follows the prior project's native app (dark, gradient CTA — see the design canvas from earlier in this project's history) with new typefaces (Bricolage Grotesque + Hanken Grotesk, `app/layout.tsx`) rather than system fonts.

## Verified

Signed up a real account through the actual browser UI, submitted a real TTS job, played the resulting audio back (through the backend's asset proxy, not a raw R2 URL — see `backend/README.md`), and confirmed the credit balance, history entry, and public/private toggle all reflect reality. Not mocked at any layer.

## Not built yet

Android, real payment top-up (the "Top up" button doesn't do anything yet), Thai/Indonesian/Spanish marketing content (ADR 0019 — the routing/content architecture is ready, the translations aren't written), a pricing page (no real numbers yet), a music-generation marketing page (no Kie models catalogued for it yet). The top-left drawer (`components/SettingsDrawer.tsx`) exists as a real icon + open/close panel on Home, but its contents are a placeholder ("coming soon") — the language switcher that will call `lib/locale.ts`'s `setLocale()` isn't built yet.

**Home = Explore = the public gallery**: built and verified, including a real bug caught along the way. Home was showing `GET /jobs` (the signed-in user's own history) under a "Your creations" heading — but the bottom nav already calls this tab "Explore", and `/app/me` already shows personal history, so it was showing the wrong feed under the wrong label. Fixed: Home now reads `GET /gallery` (ADR 0010, cursor-paginated, `api.getGallery()`), with a simple play/pause button per row (a single shared `<audio>` element, only one item plays at a time). Building that surfaced a real race condition: switching tracks quickly could silently stop both, because the *previous* item's `play()` promise rejects (`AbortError` — standard browser behavior when `.src` changes while a play request is still pending) *after* the new item's state was already set, and the naive error handler cleared `playingId` unconditionally, clobbering the newer selection; fixed by only clearing it if `playingId` still points at the item whose promise actually failed. The TTS create page also gained a "Share to Explore" toggle *before* generating (previously this only existed on the result screen, after the fact) — same toggle UI, wired to `submitTts()`'s new `visibility` option; the post-generation toggle on the result screen still exists too, for changing your mind afterward, and correctly reflects whatever was chosen upfront.

**Voice picker**: built and verified — `components/VoiceSheet.tsx`, opened from a "Select a voice" row on the TTS create page. No target-market restriction on which languages are selectable (all 82 base languages Azure/Google's real catalogs cover) — instead the payload stays small by fetching **one language's voices at a time**: `api.getLanguages()` loads the (cheap) language list once, `api.getVoices(undefined, {language})` re-fetches only when the selected language changes, mirroring the prior project's `useVoices()` hook. Selection groups by *base language* ("es"), not exact locale ("es-MX") — Azure and Google don't carve a language into countries the same way (Azure has ~22 Spanish locales, Google has 2), so a locale-level dropdown would really just be Azure's own taxonomy; picking "Spanish" pulls in every provider's matching locale variant, each voice row showing its own specific one. This grouping is alias-aware too — Google calls Mandarin Chinese `cmn`, Azure calls it `zh` (`backend/README.md`); picking "Chinese" gets both, not just Azure's. The language dropdown groups a small "Popular" shortlist (target market first — `POPULAR_LANGUAGES` in `VoiceSheet.tsx`) above "All languages" (the other 68), matching the prior project's pattern. Search/gender/provider filter client-side within the currently-loaded language (provider filter only renders once more than one provider is present). `lib/locale-names.ts` formats locale codes ("es-MX" → "Spanish (Mexico)", "es" alone → "Spanish") via the browser's own `Intl.DisplayNames` — no lookup table needed, unlike the prior project's hand-maintained one — including Azure's rarer 3-segment codes (a script subtag like `sr-Latn-RS`, or one of Azure's own dialect labels like `zh-CN-guangxi`), which an earlier, naive version silently collapsed to their base "{Language} ({Region})" name losing the distinguishing part entirely. Also cleans up Google's raw voice-id display names ("th-TH-Chirp3-HD-Achernar" → "Chirp3 HD Achernar"; Azure's own names need no cleanup). No play-preview button — deliberately cut (previewing would mean either paying to regenerate on every tap or building a sample-caching pipeline; punted rather than guessing which).

**Picking a voice is required**, not optional — the "Select a voice" row shows "Required" until one's chosen, and Generate stays disabled until then (`backend/README.md`: Fish Audio isn't a general fallback voice, it's reserved for a user's own cloned voices later, so there's no sensible default to silently fall back to).

**Audio Settings**: built and verified — `components/AudioSettingsSheet.tsx`, a second row on the TTS create page below "Select a voice" (gear icon, `Speed {x}x · Volume {n}% · Pitch {n}` summary). Same 3-tab, one-slider-at-a-time layout as the prior project's native TTS page (`lib/audio-settings.ts` ports its exact ranges/defaults/pitch-label thresholds), restyled to this project's tokens. A sticky per-browser preference — `useAudioSettings()` persists to `localStorage` (`tts_audio_settings`), not per-generation and not synced server-side, matching the prior project's own `AudioSettingsContext`. Edits are local to the sheet until Save; the sheet remounts (`key={isOpen}`) each time it opens so a cancelled edit never lingers, without needing an effect to re-sync state (this project's ESLint flags `setState` calls written directly in an effect body — both this and the settings-load-from-localStorage read use a lazy `useState` initializer or a remount key instead, never a sync effect). `speed`/`volume`/`pitch` ride along on every `submitTts()` call; the backend does the real work of converting them per-provider.

**Kie image generation** ([ADR 0015](../../docs/decisions/0015-kie-model-catalog.md)): built and verified end-to-end through the real browser, real backend, real Kie API, no mocks — the capability menu's "Text to Image" item (id `text-to-image`, previously a disabled placeholder labeled "AI Image" — renamed once "Image to Image" was about to become a second, genuinely different capability that "AI Image" could no longer distinguish itself from, `backend/app/services/menu.py`) now points at `/app/create/kie/text-to-image`, which listed the 3 real enabled models (Flux-2 Pro, GPT Image 2.5 Flare/Sunburst) with live pricing; picked Flux-2 Pro, typed a prompt, hit Generate — genuinely async under the hood (ADR 0014/0015: the response is `pending`, not already-finished, unlike TTS) — `pollJob()` kept polling until a real image came back (~1-2 minutes in this run, since local dev has no public URL for Kie's webhook, so completion depended on the 1-minute poll-sweep cron rather than an instant callback) and rendered it as an `<img>`, then "Share to Explore" made it appear on the Home/Explore feed correctly labeled and captioned. That last step caught a real, pre-existing gap: `GalleryRow` (`app/(app)/app/page.tsx`) was written audio-first — a play/pause button and `item.input.text` as the caption — so a Kie item rendered with a nonsensical play control and a blank caption (its real shape is `input.inputs.prompt`, no `input.text`). Fixed by branching on which shape an item actually has: a Kie item now shows a static image icon and falls back to `input.inputs.prompt` for the caption; a real image thumbnail in place of the icon is a reasonable next step, not done yet.

**Image to Image** ([ADR 0016](../../docs/decisions/0016-kie-image-to-image-uploads.md)): the capability menu's second Kie entry, `/app/create/kie/image-to-image` — same generic pages as Text to Image above, verified through the real browser to render every one of `flux-2/pro-image-to-image`'s 5 real fields correctly, including the first real use of the `image` field type (`ImageField`, "Add images (0/8)"). The upload-then-generate call itself is verified too (at the service layer, once `R2_PUBLIC_BASE_URL` was set up — `backend/README.md`): a real reference photo, edited by a real Kie call, came back correctly transformed, and the uploaded reference was confirmed deleted from R2 immediately after. The one leg not yet exercised through the browser itself is clicking `ImageField`'s real file picker and confirming `api.uploadKieReference()` fires from that — ordinary React file-input code, low risk, but not literally clicked through yet (this environment's browser automation can only upload files the user explicitly shares with the session, not arbitrary local ones, so this stays service-layer-verified for now).

**Image to Video** ([ADR 0017](../../docs/decisions/0017-kie-video-and-catalog-splitting.md)): the capability menu's third Kie entry, `/app/create/kie/image-to-video` — the first category with `output_type: "video"`, exercising `KieResultView`'s new `<video controls>` branch (previously only ever rendered `<img>`) for real. Verified through the real browser that `grok-imagine-video-1-5-preview`'s all 6 real fields (prompt, reference image, aspect ratio, resolution, `duration` — a plain number input reading `KieInputField.note` for its "Range: 1-15 seconds" hint, and NSFW filter) render correctly with zero page-specific code, and that the Generate button's live cost estimate (`estimateKieCost()`, extended for the new `rate_param`/`tier_param`/`rates` pricing shape) showed the right number — `20 credits` for the default 8-second/480p combination (`ceil(2.4 × 8)`). The actual submit-and-generate call is verified at the service layer (same caveat as Image to Image's upload leg — a real file can't be pushed through this environment's file input) — see `backend/README.md` for the real Grok video result and its exact credit settlement. Veo 3.1 Lite is the category's second live model — its `image_urls` field (the generic `ImageField`, `multiple: true, max: 2`) doubles as "start frame" (first upload) and an optional "end frame" (second upload), the same array-of-images mechanism Grok's own `image_urls` already uses at a higher `max`, so this needed zero new frontend code despite the two models shaping the same idea (start/end frame vs. up to 7 references) differently.

**Explore split into Voices/Images/Videos tabs** (ADR 0010, user-requested — showing three content shapes in one flat list stopped scaling once the catalog grew past a single Kie category): `GET /gallery` gained a server-side `output_type` filter (`audio`/`image`/`video`, reusing `kie_categories.output_type`, ADR 0017, rather than a second classification — `Job.capability === "tts"` is the one explicit `audio` special-case since TTS isn't a Kie category), and Home now fetches per-tab (`itemsByTab`, cached so switching back doesn't refetch) instead of one combined list. The empty-state CTA also became tab-aware — a hardcoded "Generate speech" link never made sense on an empty Images tab. Voices keeps the row-list layout (a play/pause button suits audio, which has no picture to show); Images/Videos got a real redesign, not just a filtered version of the same row — a 2-column grid of actual thumbnails with a bottom gradient-scrim caption, directly modeled on the prior project's own Image tab (a screenshot of it was the spec). Each grid cell fetches its own blob URL via the same auth'd `assetBlobUrl()` helper the audio row already used; a video cell adds a play-badge overlay and toggles muted inline playback on tap rather than opening a separate player (no per-item detail page exists, and building one wasn't asked for). Verified through the real browser: Images renders real thumbnails with correct captions and crops (`object-cover` inside `aspect-[4/5]` cells); actual video *decoding* inside this session's browser-automation tab could not be confirmed visually — a plain, non-React `<video>` given the exact same (independently confirmed valid: correct size, correct `video/mp4` content-type) blob URL also never left `readyState 0` in this specific tab, pointing at a codec/decode limitation of this automation environment rather than the component (all its attributes — `src`, `muted`, `playsinline`, `loop` — render correctly in the DOM); the play-badge overlay and toggle logic were confirmed to respond to clicks regardless.

That grid also surfaced a real, pre-existing gap in `app/(app)/layout.tsx`: nothing under `(app)` constrained content width, so every page silently relied on being viewed at phone width — invisible for a column of text rows, glaring for a 2-column image grid, whose cells stretched to absurd proportions on a wide desktop browser (caught by the user, not in review).

The first fix (`mx-auto max-w-md`, matching `BottomNav`'s own existing inner-row convention) was wrong in a different way, also caught immediately: it centered the same phone-width column with empty space on both sides on desktop — not desktop support, just a phone stranded in the middle of a browser window ("这样桌面端的客户就不用了吗？"). `frontend/web` was never actually scoped as mobile-only (ADR 0005 has it as the plain web app for any browser, Android is the separate native surface for mobile-specific needs) — the mobile-shaped design was just an unexamined default every page inherited, not a decision. Asked the user to settle the real fork this implies (switch to a desktop sidebar nav vs. keep the bottom nav and only widen the content shell); they picked the latter, so:
- `lib/layout.ts` exports one shared `APP_CONTENT_WIDTH` (`max-w-md md:max-w-2xl lg:max-w-4xl`) — phone width by default, genuinely wider on real desktop viewports, not a fixed extra-wide phone. Used by both `(app)/layout.tsx` (the actual page content) and `BottomNav`'s inner row, so the nav stays visually aligned with the content above it at every breakpoint instead of the two drifting apart.
- Explore's grids gained matching breakpoints (`grid-cols-2 md:grid-cols-3 lg:grid-cols-4`) — the actual point of the wider shell: more thumbnails visible at once on desktop, not 2 giant ones.
- `fixed`-positioned overlays (`SettingsDrawer`, `CreateSheet`) are unaffected either way — a plain wrapper `div` creates no new containing block for `position: fixed` descendants, confirmed both still span the true viewport edges, not the narrower content column.
- Verified at a real ~1920px desktop width: Explore's Images tab now shows compact, correctly-proportioned thumbnails (roughly a quarter of the wider shell each) instead of two huge ones, and `BottomNav`'s three icons spread across the same width as the content above rather than sitting in a narrower island beneath it. Mobile behavior (everything below the `md:` breakpoint) is provably untouched — only `md:`/`lg:` overrides were added on top of the pre-existing default classes, nothing below that breakpoint changed. One acknowledged non-goal: individual single-column pages (the TTS/Kie generation forms) now sit inside a wider shell too, but weren't each re-tuned to use the extra width themselves — the shell being wider doesn't force every page's own content to stretch to match it, and a plain form arguably shouldn't; revisit per-page if any of them look sparse rather than assuming they all need it.

**Voice cloning** ([ADR 0009](../../docs/decisions/0009-voice-cloning-reusable-asset.md)): built and verified — `app/(app)/app/create/clone/page.tsx`, one page with a Generate/Clone tab switch, mirroring the prior project's own `/native/create/clone` (CLAUDE.md: "增加一个菜单，然后在一个页面里完成"). Scoped to a user's *own* cloned voices only — the prior project's Generate tab also browsed Fish Audio's public voice marketplace; that's a separate, undocumented feature and out of scope here. Clone tab: `components/AudioRecorder.tsx` (record or upload a short sample) + a name + an optional transcript, `POST /voice-models` (multipart); lists existing cloned voices with delete. Generate tab: pick one of those voices, type text, reuses the same Audio Settings sheet and "Share to Explore" toggle as the TTS create page, `POST /generate/tts`'s `voice_model_id`. Verified end-to-end through the real browser: trained a real voice from an uploaded sample (mic recording itself isn't automatable without a real microphone, so this leg was tested via the file-upload fallback, which drives the same code path as a completed recording) → it appeared as "Ready" immediately (training is synchronous, `backend/README.md`) → generated real speech with it (7 credits charged, real audio played back) → deleted it (204). Caught a real backend bug this way — see `backend/README.md`'s ADR 0009 paragraph.

Both tabs show each cloned voice's real name (`title`, the one typed into the Clone tab), never a generic placeholder — this wasn't the original design. It was added after a real incident where the first version had no name at all (every voice showed as identical, indistinguishable text), and a real user's just-trained voice got deleted by mistake because it couldn't be told apart from test data. See `backend/README.md`'s second ADR 0009 paragraph for the full story.

**Background job execution** ([ADR 0014](../../docs/decisions/0014-background-job-execution.md)): the TTS and Clone create pages' "Generate"/"Create clone" buttons originally did submit-then-poll — `api.pollJob()` right there on the same screen — rather than assuming the first response was final. That pattern is gone now; see **Real-time job updates** below for what replaced it and why.

**Real-time job updates** ([ADR 0018](../../docs/decisions/0018-realtime-job-updates-sse.md)): every create page (TTS, Clone's Generate/Clone tabs, Kie image/video) submits and returns control immediately now — a toast, the form stays usable, no more blocking `pollJob()` anywhere, prompted directly by the user catching a real screenshot of a Kie form stuck on "Generating…" and pointing out that a backend that's already async shouldn't make the frontend pretend otherwise. `lib/job-events.tsx`'s `JobEventsProvider` (wraps `(app)`'s page content, `app/(app)/layout.tsx`) opens one `EventSource` against `GET /events` for the session — reconnecting by hand with a fresh ID token on every drop rather than trusting `EventSource`'s own built-in retry, which would keep reusing the token snapshotted at first connect (stale after about an hour). It exposes `registerPendingJob()` (called right after a successful submit) and `lastEvent` (the most recent `{job_id, status, capability}` an SSE message delivered) via context. `BottomNav`'s "Me" icon carries a small badge for how many of the user's own jobs are still in flight; `/app/me` is where a result is actually viewed — every job card shows live status (spinner while pending/processing, the real error inline if failed, the actual audio/image/video once succeeded, reusing the same `assetBlobUrl()` pattern Explore's own media grid already established) and live-patches in place via `GET /jobs/{id}` the moment its own event arrives, rather than the event payload trying to carry a full result itself.

**Two follow-up fixes to `/app/me`, both caught by the user on a real account with 31 real jobs**, not a small dev-only seed list: "数据一多 就很慢啊" (it gets slow once there's a lot of data) — `JobMedia` originally fetched every visible card's asset via `assetBlobUrl()` eagerly, on mount, the same trade-off Explore's own grid made; fine for a handful of items, genuinely slow at 31 concurrent authenticated fetches. Fixed with an `IntersectionObserver` per card (a generous 400px `rootMargin` so scrolling to it still feels instant) — the fetch now only starts once a card is actually near the viewport, confirmed live: only 7 of 31 assets requested on initial load, the rest staying untouched until scrolled to. The second ask — "加个标签 All Voices Images Videos" — added the same tab pattern Explore already uses, filtering the already-fetched job list client-side (no new endpoint; `GET /jobs` already returns the signed-in user's full history in one call, unlike Explore's public, cross-user, genuinely-paginated gallery). Voice-clone *training* records (no playable media) live under "Voices" here too, since this list is the only place they show up at all.

Verified through the real browser end to end, not just the API directly: submitted a real Azure TTS job → watched the bottom-nav badge go `1 → 2` on submit → the real backend worker (a separate, already-running process) pick it up and finish it for real → the badge drop back to `1` the instant its SSE event arrived, no reload, no poll → `/app/me`'s own card for that job flip from a spinner to a genuine, working `<audio controls>` player in place. One real testing mistake caught and worth remembering: a voice-picker sheet that visually looked selected but hadn't actually registered the click made the first two submit attempts silently no-op — confirmed via `read_network_requests` showing zero calls to `/generate/tts`, not assumed from how the UI looked; a screenshot that looks right isn't proof a click landed.

**i18n routing** ([ADR 0013](../../docs/decisions/0013-i18n-routing-strategy.md)): `(marketing)` will use locale-prefixed URLs once it exists; `(app)` uses a plain cookie (`lib/locale.ts`'s `getLocale()`/`setLocale()`) — already wired into `CreateSheet`'s `GET /config/menu` call, just nothing writes the cookie yet since the language switcher isn't built.
